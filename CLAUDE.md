# clabox

> **This file contains instructions for AI assistants (Claude).** For project documentation see [docs/guideline.md](docs/guideline.md).

Run Claude Code in a sandbox for super-safe YOLO mode, configured in plain JavaScript.

**Important:**
- **ALWAYS** update this file and docs/guideline.md when changing scripts, structure, dependencies, commands, env vars, or the generated SBPL rules — do it in the same step, not after
- Runtime deps are **`yargs`** (CLI parsing) and **`@lsk4/log`** (pretty CLI logging, used only in `cli.ts`) — keep `@lsk4/log` out of `src/index.ts`/`src/info/` so the public `lib/index.js` stays dependency-light under the size-limit
- Run `bun run fix` and `bun run test` after each code change
- **Before saying "done"**, run the full `bun run test` (lint + types + unit + size). Functional tests shell out to real `sandbox-exec` and auto-skip off macOS or when nested in a sandbox — on macOS they must run, not be skipped
- Always write tests for new functionality — for profile changes, assert the generated SBPL text in `tests/profile.test.ts`
- Never invent SBPL rules: the profile must pass `sandbox-exec` validation. Test profile changes against real `sandbox-exec`
- Default to **Bun** for dev/test/build. The published `lib/` is plain ESM that runs on **Node ≥ 18**; the only runtime dependency is `yargs`

## Main Commands
```bash
bun install              # install deps (lockfile: bun.lock)
bun run build            # tsdown → lib/ (ESM + .d.ts + sourcemaps)
bun run test             # lint + types + unit + size (run before "done")
bun run fix              # biome check --write (format + lint + import order)
bun test                 # unit only (bun:test)
bun run cli -- profile   # run the CLI from source (also: generate, run, init)
bun run cli -- info      # print version + resolved box/config/extras diagnostics (via @lsk4/log)
bun run cli -- init      # gen clabox-<name> aliases + build Ghostty apps for `app` boxes
bun run cli -- init --no-apps        # aliases only (skip the Ghostty-app build)
bun run cli -- init --app "AX Manager" # (re)build just one app box
bun run cli -- -b ax-root # run a named box from ~/.config/clabox/configs/*.config.mjs
bun run cli -- -b ./boxes/vibe.mjs # run a box straight from a config-file path
bun run cli -- --ro ~/dir2 run       # ad-hoc read-only grant (repeatable)
bun run cli -- --stat ~/Library run  # ad-hoc stat-only grant (metadata, no contents)
bun run cli -- --ro ~/a --rw ~/b run # ad-hoc RO + RW grants (both repeatable)
bun run cli -- -b ax-mg --rc                    # unset ALL vars that block feature flags (→ /rc) + grant the daemon socket + mark the tab
bun run cli -- -b ax-mg -e DISABLE_TELEMETRY    # unset a preset/shell var for THIS tab (→ /rc works)
bun run cli -- -b ax-mg -e DISABLE_TELEMETRY=1  # …or force it on for this tab only
bun run cli -- -b ax daemon          # claude's Remote Control daemon, OUTSIDE the sandbox
bun run cli -- --name ax daemon --detach # …in the background (`--name` is an alias of `-b`)
bun run cli -- -b ax daemon status   # passthrough: run | status | stop [--any] | logs
bun run cli -- -b ax-mg tab          # open that box in a new tab of the RUNNING Ghostty
bun run cli -- -b ax-mg tab --split right --rc  # …as an --rc split next to this one
bun run cli -- -b ax-mg tab --print  # print the AppleScript instead of running it
bun run cli -- opener --detach       # ONE opener broker, OUTSIDE the sandbox, serves every box
bun run cli -- opener --root ~/vault --editor Obsidian # …with an explicit policy
bun run cli -- reveal .              # (in ANY box) show this dir in Finder
bun run cli -- open ./notes/a.md     # (in ANY box) open a file in your editor
bun run cli -- trust ./clabox.config.mjs # record a config OUTSIDE ~/.config/clabox as trusted
bun run cli -- trust --list          # …list the records (⚠️ = edited since it was trusted)
bun run cli -- --trust -b ./boxes/vibe.mjs # accept an untrusted / box-writable config for ONE run
bun run cli -- init --dir ./repo --trust   # `init` imports EVERY config it finds → same gate
```

## Structure

**Rule:** Only entry-point files live in `src/` root — `index.ts` (public API aggregator) and `cli.ts` (the CLI, built to `lib/cli.js` = the `clabox` bin). All other code lives in subdirectories. The build emits to `lib/`; `bin`/`main`/`exports` point at built `lib/*.js`.

## Key Architecture
- **11 CLI commands** (`run` / `generate` / `profile` / `info` / `init` / `daemon` / `tab` / `trust` / `opener` / `reveal` / `open`) over a pure builder (`sandbox/profile.ts`) and an I/O launcher (`sandbox/run.ts`) — keep that pure/I-O split
- **`info`** (`info/info.ts`) is the introspection report (who/what clabox is for the resolved config): `gatherInfo(config, {configFile, box, trust})` does the I/O snapshot (resolve `claude`/`sandbox-exec` via `which`, `process.argv[1]`/`execPath`, profile path, compiled extras, tracked `CLABOX_*` env) and `formatInfo(data, {color})` is the pure aligned-text builder (color gated on a TTY). The CLI prints it through `@lsk4/log` (`createLogger('clabox').log(...)` for the table, `.warn(...)` when `claude`/`sandbox-exec` is missing). It also prints the two things that decide how confined a box really is: the `escapes` row (`info.ts#escapeHatches` — `allowBackgroundTasks` / `allowOpen` / `remoteControl`, `(none)` by default) and the config file's trust state. **Version + self-path** come from `resolveClaboxPackage()`, which **walks up from `import.meta.url` to the `package.json` whose `name === 'clabox'`** — a fixed `../../package.json` breaks once tsdown hoists the code into a hashed chunk (`lib/info-<hash>.js`) at a different depth; the walk survives the source tree, the built tree and an installed `node_modules/clabox/`
- `init` mirrors that split: `init/aliases.ts` + `init/ghostty.ts` are the pure text builders, `init/scaffold.ts` + `init/app.ts` do the fs/exec I/O. It discovers boxes in `<dir>/configs` (default `<dir>` = `defaultBaseDir()` = the parent of the global `configsDir()`, i.e. `~/.config/clabox`, honoring `CLABOX_CONFIGS_DIR`; overridable via `--dir` for a project-local `<dir>/configs` layout) via the same `listBoxes` rules as `-b` (both `<name>.mjs`/`<name>.config.mjs`, `_`-partials skipped) and (re)writes `<dir>/scripts/`: a source-able `index.sh` plus one `clabox-<name>.sh` wrapper per box. Each command runs `clabox -b <name>` — yolo vs. safe is decided by the box's own preset (`claudeArgs`), **not** by `init`. It prunes its own stale artifacts (`index.sh`, `clabox-*.sh`) on each run. **Paths are resolved at run time, not frozen at init time**: the `clabox` command is emitted bare so the shell's PATH resolves it at launch (survives package-manager moves, e.g. bun → npm/homebrew); `CLABOX_CONFIGS_DIR=<dir>` is baked **only when `<dir>/configs` doesn't already resolve (realpath, symlinks included) to the runtime default `~/.config/clabox/configs`** (`bakeConfigsDir`) — when it does, the prefix is omitted and `-b` finds the box via the default. The project `cd` dir stays absolute (it doesn't move with the package manager). An explicit `appBuilder.claboxBin` still pins an absolute binary path
- **Ghostty apps from `init`**: a box opts in by carrying an `app` object (`AppConfig`) in its config — only then does `init` `loadConfig` that box, write a Ghostty config to `<dir>/ghostty/<name>.config` (a `command = zsh -lic '…'` — login+interactive so the GUI app inherits the user's PATH, not launchd's minimal one — that `cd`s into `config.cwd` and runs `clabox -b <name>`; the `cwd`/`CLABOX_CONFIGS_DIR`/`claboxBin`/box name are double-quoted (`ghostty.ts#shQuote`) so a spaced path like iCloud's `~/Library/Mobile Documents/…` doesn't split `cd` into two args (`string not in pwd`), plus `title`/`macos-icon`/extra lines from `app`), and build a cloned `<appsDir>/<name>.app` (replacing the old `ghostty-app-builder.sh`). The clone steps live in `init/app.ts` (macOS-only) and build into a staging `<name>.app.new` that is atomically `rename`d onto `<name>.app` **only after every step succeeds** — a failed build (e.g. an unreadable donor) never destroys the existing bundle: extract entitlements, `cp -R` Ghostty.app into the stage, patch `Info.plist` (identity, Sparkle off, and `LSEnvironment`), set the icon (`.icns` copy or `.png`→`sips`+`iconutil`, then `plutil -remove CFBundleIconName` so macOS uses our loose `.icns` instead of the icon baked into Ghostty's `Assets.car`), disable Sparkle, `codesign` (`appBuilder.signId` or ad-hoc `-`). Machine-wide build settings live in `config.appBuilder`. It also writes a Raycast script command per app box to `<dir>/raycast/<name>.sh` (`init/raycast.ts#buildRaycastCommand`: `@raycast.*` metadata + `open <appPath>`; icon = `app.emoji` → the title's leading emoji → 👻). `--no-apps` skips the build; `--app <box|name>` (re)builds one. Builds are best-effort: if the host can't build (`canBuildApps`: not macOS / no Ghostty) or a build throws, it records a warning and still emits the aliases (and the ghostty config + raycast script, which point at where the app will live). It prunes its own `<dir>/ghostty/*.config`, `<dir>/ghostty-home/*` and `<dir>/raycast/*.sh` on a full run (not with `--app`, which would orphan other apps' artifacts). `.app` bundles are **not** auto-deleted
- **The clone keeps the donor's binary — a launcher wrapper destroys its identity** (`init/ghostty.ts#ghosttyHomeDir`): the config reaches the app through `LSEnvironment = {XDG_CONFIG_HOME: <dir>/ghostty-home/<box>}` in `Info.plist` (macOS exports it for every LaunchServices start — Dock/Finder/`open`/Raycast) plus a one-line `<dir>/ghostty-home/<box>/ghostty/config` holding `config-file = <dir>/ghostty/<box>.config`. The obvious alternative — rename the real binary to `ghostty.real` and make `CFBundleExecutable` a C wrapper that re-execs it with `--config-file=` — is what the builder did until it was found to break every bundle-identity consumer. **LaunchServices keys its record on the running executable path**, so when the image changes under it — `execv` included, which keeps the pid — it moves the launch data to `originalExecutablePath`/`originalPid` and **clears the `pid` field**. Observable in `lsappinfo info <bundleid>`: a healthy app prints `pid = <n>`, the wrapped clone prints no `pid` line at all and `NSRunningApplication.processIdentifier` returns **−1**. Anything that goes bundle → pid → API then silently no-ops: a window manager calls `AXUIElementCreateApplication(-1)`, gets an empty window list and can't move the windows (how this was found: Rectangle ignoring one app), and AppleScript targeting and Dock integration break the same way. TCC is hit from the other side — a wrapper leaves the real binary signed standalone (`Identifier=ghostty`, `Info.plist=not bound`), so prompts come from an identity that isn't the bundle's. **Never reintroduce a wrapper binary**; `ghostty.real` must not exist in a built bundle. Caveat: Ghostty also reads `~/Library/Application Support/com.mitchellh.ghostty/config`, whose path is hard-coded to the upstream bundle id (a clone cannot get its own) and which wins over the XDG path when non-empty — `init/app.ts#conflictingUserConfig` warns when that file exists. Since `XDG_CONFIG_HOME` is inherited by everything the terminal spawns (`gh` reads `$XDG_CONFIG_HOME/gh/hosts.yml`), the generated `command` drops it again — **conditionally**, `[ "$XDG_CONFIG_HOME" = <ours> ] && unset …`, because `zsh -lic` has already re-exported a user's own value from the login profile by then. See docs/troubleshooting.md
- **`appBuilder.baseGhosttyConfig` leaks into every clone** — it's emitted as the leading `config-file`, so whatever lives in the shared base config is inherited by all app boxes. The one that bites: a `keybind = global:…` (e.g. `global:cmd+backquote=toggle_quick_terminal`) needs a global event tap, a tap needs **Accessibility**, and so *each* clone prompts "would like to control this Mac" on *every* launch (denying doesn't stick). Keep `global:` keybinds in the personal `~/.config/ghostty/config`, which only the real Ghostty reads; per box, `app.ghostty` can `keybind = <trigger>=unbind` (emitted after the base config, so it wins — but `app.ghostty` is a `Record<string, string>`, i.e. one keybind per box). Granting Accessibility is the wrong fix: it silences the prompt and then every clone plus the real Ghostty races for the same hotkey. Not yet automated — `init` could parse the base config and unbind the globals itself. See docs/troubleshooting.md
- **`init` input is validated, because a box config can come from a repo** (`init/ghostty.ts#assertSafeAppName` / `#assertSingleLine`, `utils/config.ts#assertSafeBoxName`): `app.name` names `<appsDir>/<name>.app`, a path the builder `rm -rf`s before cloning onto it — unvalidated, `name: '../../../tmp/x'` deletes an arbitrary directory and `name: 'Ghostty'` with the default `appsDir` eats the donor app (`buildApp` asserts `appPath !== ghosttyApp` too). So the name must be a plain filename (spaces and emoji fine — `"AX Manager"` is real — but no `/`, no `..`, no leading `.`, no control chars), `bundleId` is restricted to the reverse-DNS charset, and **every value interpolated into a generated line is rejected if it carries `\r`/`\n`/`ESC`** rather than escaped: a Ghostty config is `key = value` per line, so a newline in `cwd` or `app.title` injects a *second* `command =` (scalar keys are last-wins → it runs at every app launch, outside the sandbox). Box names are checked against `^[A-Za-z0-9][A-Za-z0-9._-]*$` by `listBoxes` (a hostile filename is simply not a box) and by `resolveBox`; the Raycast builder flattens its `@raycast.*` comment values, since a comment is only a comment up to the first newline
- **`daemon` runs claude's Remote Control supervisor OUTSIDE the sandbox** (`daemon/daemon.ts`, pure `buildDaemonArgs`/`buildDaemonEnv` + I/O `runDaemon`). Remote Control (`/rc`, sessions driven from the Claude app) needs a supervisor daemon; it's a **singleton per Claude config dir** (socket `/tmp/cc-daemon-<uid>/<hash(configDir)>/control.sock`) that claude starts **on demand**, so whoever asks first owns it. Born inside a box it is crippled two ways: (1) it probes its own start time by exec'ing `/bin/ps`, which is setuid **root** — Seatbelt refuses to exec any setuid/setgid binary (`forbidden-exec-sugid`) however wide the `process-exec` grant is — so it logs `own process start-time probe failed twice — writing a procStart-less lock` and can no longer be stopped by `claude daemon stop`, while a new daemon "never displaces a running one"; (2) a macOS sandbox is **inherited and cannot be dropped**, so every worker it spawns for a remote session stays confined to *that* box's profile and dies on another project (`bg settled … (crashed): exit 1 before init`). `clabox -b <box> daemon [run|status|stop [--any]|logs]` therefore spawns `claude daemon …` with the box's `configDir` + `config.env` but **no `sandbox-exec` and no `ulimit`**; `--detach` backgrounds it (`spawn` + `detached` + `stdio: 'ignore'` + `unref`, output goes to `<configDir>/daemon.log`). Start it before/independently of the boxes and their `/rc` reuses it. `--name` is an alias of `-b`/`--box`
- **`open` is a sandbox ESCAPE and is off by default** (`config.allowOpen: false`, env `CLABOX_ALLOW_OPEN=1`): `profile.ts` emits `(allow lsopen)` **plus** the Launch Services mach services (`com.apple.coreservices.launchservicesd`, `CoreServices.coreservicesd`, `lsd.modifydb`, `^com\.apple\.lsd(\..*)?$`) only for a box that opts in. Why it's an escape and not a convenience: `open` forks nothing in-box — it hands a path to LaunchServices, which lives outside every sandbox and starts the target as a fresh process under **launchd (PPID 1) with no Seatbelt profile**. The box can write `.app` bundles into `/tmp`, `$TMPDIR` and the project dir, so the two halves compose into arbitrary code execution as the user — measured: a 3-line `Contents/MacOS/run` opened with `open -W` came up with `ppid 1` and wrote `$HOME/ESCAPE.txt`, a path the box cannot even `touch` (and then couldn't `unlink`). Unlike the background-task escape it needs **no running daemon**, so it is always available. The profile already withholds `appleevent-send` for exactly this reason ("would let a sandboxed claude script your terminal"); `lsopen` was the same hole under another name. `com.apple.lsd.mapdb` **stays** granted — it's the read-only type/UTI database many frameworks consult and it cannot start anything. The operation and the mach services are emitted **together**: the gate is checked by the receiving service, so denying `lsopen` while leaving its ports reachable would be half a fix. A box that genuinely needs `open` (a URL-opening helper) sets the flag and is then no more confined than `allowBackgroundTasks` makes it; in-box `/login` can't pop a browser either way, so log in from an unsandboxed shell
- **The opener BROKER is the safe slice of `open`** (`src/opener/*`): `allowOpen` is all-or-nothing because `lsopen` takes no filters, but what a user actually wants from it is narrow — "show me this folder", "open this file in my editor". So **one** `clabox opener` runs outside the sandbox on `<claboxHome>/opener/opener-<uid>.sock` (`0600`; under the clabox home, not `$TMPDIR`, which is RW for every box) and **every** box reaches it with `clabox reveal <dir>` / `clabox open <file>`. One broker, not one per box, because a box only ever *sends a path*: the result — a Finder window, an editor tab — lands in front of the user and never goes back into the box, so there is nothing per-box to isolate. Policy (`roots`, `editor`) belongs to the broker, from its own config or `--root`/`--editor`; the socket is granted to every box unless it sets `opener: { enabled: false }`, and since the socket only exists while a broker runs, the grant alone opens nothing. The security property is that **the agent supplies a path and nothing else**: the wire format is `<action> <absolute path>`, one line, **no flags** (one `-a`/`-b`/`--args` and the agent picks what runs again), the action vocabulary is closed (`reveal`/`edit`), and `reveal` compiles to `open -R` — documented as "Reveals the file(s) in the Finder *instead of opening them*", so it cannot launch anything, `.app` bundles included. `edit` goes to `open -a <app>`, and **which** app is decided by `opener/routing.ts` from the file type plus what `opener/apps.ts` found installed: code/text → the first of `CODE_EDITORS` present (Zed, Cursor, VS Code, Sublime, Nova, …), a `.md` inside an Obsidian vault (a `.obsidian` dir above it) → Obsidian, a `.md` **outside** a vault → the first of `MARKDOWN_APPS` present (Typora, MacDown, Marked 2) and only then the code editor — `open`ing a doc is a request to *read* it, and the agent edits markdown with the file tools rather than through an app, so the rendered reader wins where one is installed and nothing changes where none is — an image/PDF → Preview, nothing found → `open -t`. An explicit `--editor`/`opener.editor` wins over all of it. The two fallbacks that were tried first are in the code as a warning: the type's **registered handler** (plain `open <file>`) opens `.md` in **Xcode** on a normal Mac — which then demands to install system components — and `-t` lands in **TextEdit**. Neither is where anyone reads code, and "configure it yourself" is a poor answer for a convenience. Routing changes nothing about the security story: the agent still sends only a path, every branch is an app the user already has for that kind of file, and the broker reports which one it used (`ok: Zed`). Each request is `realpath`ed (a symlink inside a root is how an in-root path points at `/Applications`), must land inside the roots (default `$HOME`), must not touch a bundle (`.app`/`.bundle`/`.framework`/`.xpc`/`.appex`), and for `edit` must match `DEFAULT_EDIT_EXTENSIONS` (never `.command`/`.scpt`/`.app`/`.pkg`…). A missing path answers exactly like an out-of-root one, so the broker is no existence oracle; requests are rate-limited (12/min — fifty Finder windows are a fine place to hide the one you'd have objected to) and every decision lands in `<claboxHome>/opener/opener.log` — socket, pid, log **and** the generated shell helpers share that one dir (`utils/config.ts#openerDir`), so `ls` answers what the broker owns on disk. **The helpers are generated, not documented** (`opener/aliases.ts`, pure → written by `runOpener` to `<claboxHome>/opener/claude-aliases.sh`, `0644`, rewritten on every start, printed by the CLI with its `source` line). **They speak to the socket directly with `nc -U` and never run `clabox`** — the wire format is one line, the box already has the socket grant, and exec'ing clabox in a box needs a grant on wherever its binary *physically resolves*: for a dev install (`npm link`) that is clabox's own source repo, a path no other box grants, so a helper built on `clabox reveal` dies with `operation not permitted: clabox` before the socket is ever touched. `nc` is in `/usr/bin`, which the base policy already grants `rme`, so the helpers need **no new grant at all**. The socket path is baked in at generation time (the broker writes the file, so the two cannot drift), and `_cb_abs` makes the path absolute with `cd`/`pwd` rather than `realpath` (absent on some systems, and pointless — the broker realpaths and roots-checks anyway). This is also why the server answers with `conn.end`, **one request per connection**: it used to `write` and hold the connection open for more lines that nothing ever sent, which made `printf … | nc -U <socket>` print the answer and then hang forever. Beyond that, the correct helper is not one line. `clabox open` refuses a **directory** (no extension in `DEFAULT_EDIT_EXTENSIONS` → `denied: file type not allowed`), so a folder has to go to `reveal` and a file to `open`; a URL can't go to the broker at all (absolute paths only); and **outside** a box the native `open` is still the right answer, so the helper branches on `_cb_inbox` (`[ ! -r /Applications ]` — clabox exports no in-box marker and `/Applications` is granted to no box). POSIX shell, so it sources in bash and zsh, and **functions, not aliases** — claude's `!` bash mode runs a *non-interactive* shell where zsh aliases don't expand (`!o .` → `command not found: o`). Opener business only: it is rewritten per start, so anything personal belongs in the rc that sources it. Under the clabox home because the box has to *read* it, which the post-deny carve-out already allows. `open` is `execFile`d, never a shell. **The honest residual:** an editor may execute what it opens (Obsidian runs vault plugins and dataviewjs, VS Code has tasks) — the broker doesn't create that risk (the agent already writes those files and you already open them by hand) but it does let the agent choose the moment. Binding the socket needs `network-bind`, which no box has, so a broker started *inside* a box fails with a message saying where it belongs
- **Networking is split by address family — `(allow network*)` is never emitted** (`profile.ts` "networking" + "unix-socket connect"): with `network: true` the profile grants `(allow network-outbound (remote ip))` + `(allow network-inbound (local ip))` + `(allow network-bind (local ip))`, and **unix sockets are opt-in per path** (`paths.socket`, the per-path `'c'` right, or `--socket`). The old blanket line was far wider than "the box may use the internet": in Seatbelt a unix-socket `connect(2)` is authorized as **`network-outbound` with a path filter** (Apple's own profiles: `(allow network-outbound (remote tcp) (literal "/private/var/run/mDNSResponder"))`), so one unfiltered rule handed every box every socket on the machine — 1Password's `t/agent.sock` (ask the agent to sign ⇒ authenticate as the user: `git push`, `ssh` to prod), `/var/run/docker.sock` (root on the host, outside every box), gpg-agent, `op`. **No file rule ever governed this** — `paths.deny`, `denyGlobs` and the hard secret deny are all `file-*` operations, so a box denied read+write+stat on the 1Password container could still run `ssh-add -l` against the agent inside it (measured). **One** default stays in the allowlist, because removing it breaks something that reads as unrelated: `/private/var/run/mDNSResponder` (the system resolver — without it name resolution fails and it looks like "claude can't reach the API"). claude's daemon dir `/private/tmp/cc-daemon-<uid>` is **no longer** a default: it follows the feature that needs it (`config.remoteControl`, which `--rc` sets, or `allowBackgroundTasks`). It is the channel to the singleton `claude daemon`, which runs outside every box and can re-host the session with `--fork-session --resume` and no profile — the escape itself is closed in the env by `SANDBOX_ESCAPE_GUARDS`, but that guard is **cooperative** (a var inside a process the agent controls), so a box that never uses `/rc` has no reason to keep the channel open. A `paths.deny` path also loses socket connect (the soft tier emits a matching `deny network-outbound`), and each socket grant is emitted as **both** `literal` and `subpath` so a box needn't know whether it named a socket file or a dir of them. Socket grants are emitted even with `network: false` — local IPC is not internet access
- The Seatbelt profile starts with `(deny default)` — nothing is allowed unless an explicit rule grants it
- **Claude runtime state (RW)**: `~/.local/state/claude` (claude's startup version lock — it writes a `.lock.tmp.<rand>`, so RO isn't enough) and `~/Library/Caches/claude-cli-nodejs` (per-MCP-server log batches). Both are claude-owned scratch dirs with no credentials in them (OAuth tokens live in the keychain); `~/.cache/claude` stays RO. Symptoms of dropping these: `NON-FATAL: Lock acquisition failed` / `Dropping log batch for …` in `<configDir>/debug/latest`
- **`~/.local` is granted per toolchain, never as one tree** (`policy/base.ts` "package managers & user-installed toolchains"): this used to be `profile.ts#detectPackagePaths()`, an `existsSync` probe that found Homebrew / Nix / `~/.local` and granted each one `rme` **as a subpath**. `~/.local` exists on every machine (claude installs itself there), so one `existsSync` handed every box `(subpath "~/.local")` — and XDG puts *application data* under `~/.local/share`, so that rule silently covered app databases, notes and chat history that no box config ever mentioned and no line of the profile ever named. **The probing is gone entirely**: a rule for a path that doesn't exist matches nothing, so Homebrew (both locations), `/nix/store` and each `~/.local` toolchain root are plain base-policy data, visible in the config and overridable per box. `~/.local/bin` alone authorizes **nothing** — every entry there is a symlink into `~/.local/share/<tool>/…` and Seatbelt matches the resolved path, so each target root is listed by name (`claude`, `mise`, `uv`, `pipx`, `pnpm`, `rustup`); `~/.local/share/claude` is load-bearing, since that is where the native installer puts the binary clabox execs. Anything else under `~/.local/share` is **not** granted — a box that needs one adds `'~/.local/share/<tool>': 'rme'`
- **Active toolchain grant (`profile.ts#resolvedDeveloperDirs`)**: `/Library/Developer/CommandLineTools` + `/Applications/Xcode.app` are granted statically, but `/usr/bin/python3` (like `clang`/`git`/`swift`) is a **shim that execs whatever `xcode-select -p` selects** — and Seatbelt matches the **symlink-resolved** path. On a dev mac `Xcode.app` is a real directory, so the static grant covers it; on a CI runner the bundle is versioned (`/Applications/Xcode_16.4.app`) with `Xcode.app` a symlink onto it, the static grant resolves to nothing, and CPython dies at preinit — which showed up as the entropy regression test passing locally and failing only in CI. So the profile also grants the realpath of the link `xcode-select` maintains (read via `fs`, not by shelling out), minus whatever is already static. Same class of bug as the resolved clabox home. **The link itself must be granted too, and its location moved**: a shim reads the link *before* it execs anything, so a granted bundle behind an ungranted link buys nothing — every shim dies with `xcode-select: error: unable to read data link at '/var/select/developer_dir'`, i.e. **no `git` and no `python3` in the box at all**. Apple relocated it (`/var/db/xcode_select_link` ≤ macOS 15, `/var/select/developer_dir` on 26+), so `XCODE_SELECT_LINKS` reads both and `BASE_PATH_GROUPS` grants both — reading only the old path silently resolves to nothing on a current mac, which looks exactly like "no Xcode installed". `/var/select` is granted as a **tree**, not just that one link: it's the system's alias dir, and `/var/select/sh` is read by *every* `/bin/sh` startup — denied, each shell prints `Error opening /private/var/select/sh: Operation not permitted` into unrelated command output
- **Every grant under `/etc`, `/tmp` or `/var` MUST be spelled resolved** (`utils/config.ts#PRIVATE_SYMLINK_ROOTS` + `resolvedTwin`, enforced by a unit test): macOS ships those three as symlinks into `/private`, and Seatbelt matches the **resolved** vnode path — `'/private/var/db/timezone'` is what lets a tool open `/var/db/timezone`, while a rule written `'/var/db/…'` matches *nothing*. The failure mode is the nasty one: the rule is right there in the profile, `sandbox-exec` accepts it, and the access is still denied. The `literal` trick that makes `/etc` work **does not generalize** — it works because `/etc` *is* the symlink, so reading the link is reading that path; a path *below* a symlinked root is a different vnode. This has shipped broken twice: `/etc/ssl` (see the next bullet) and `/var/select/developer_dir`, where the first attempt granted `'/var/select': 'r'` + a literal `'/var/db/xcode_select_link'`, authorized nothing, and left every box without `git` or `python3` — the exact symptom it was written to fix. `tests/profile.test.ts` now asserts the `/private` twin exists for every base-policy path, so the next one can't ship silently. **A profile fix also does not reach a box that is already running** (Seatbelt is applied at `exec` and never re-read) — fix, then open a new box; see docs/troubleshooting.md
- **A symlinked system dir needs BOTH forms granted** (`BASE_PATH_GROUPS`): Seatbelt matches the resolved path, so the resolved grant is what authorizes the open — but walking a path through a symlinked ancestor also *reads the link*, and the stat-ancestors pass only climbs **above** granted paths. `/private/etc` was granted while `/etc` was not, and since nothing is granted *under* `/etc` no ancestor rule ever covered it: every lookup through `/etc/...` failed on the link. The visible symptom was the system `curl` rejecting **all** HTTPS (`error setting certificate verify locations: CAfile: /etc/ssl/cert.pem`, `http_code 000`) — which reads as "the box has no network", though `node`'s `fetch` works fine and `curl --cacert /private/etc/ssl/cert.pem` returns 200. `/etc` is therefore granted `'sl'` = `file-read-metadata` + `literal`: the link only, never a tree below it (contents still come from `/private/etc`). `/tmp` + `/private/tmp` were already spelled out as such a pair; treat that as the pattern, not as a quirk
- **`~/.npm` is read-write** (`BASE_PATH_GROUPS` "package-manager caches"): npm `mkdir`s `_cacache/tmp` on *every* command, `npm view` included, so read-only is not enough. Worth knowing because npm **reports the wrong cause** — it answers any EPERM under its cache with `Your cache folder contains root-owned files … run sudo chown`, so a confined box looks like a corrupted install and the suggested `chown` changes nothing. No credentials live there (the auth tokens are in `~/.npmrc`, which this does not grant)
- **Seeing & killing your own processes** (`profile.ts` "process control" + `sandbox/proctools.ts`) — three separate breakages, so fixing one alone changes nothing visible. **(1) `signal` was ungranted**, so `(deny default)` made every process the agent spawned immortal; the profile now emits `(allow signal (target self) (target children) (target same-sandbox))` plus `(allow process-info-setcontrol (target self))` (= `setpriority(2)`, without which zsh job control fails a plain `cmd &` with `nice(5) failed`). The **`target` filter is what keeps this non-global**: `children` covers direct spawns, `same-sandbox` the rest of the tree (the profile is inherited across fork/exec and can't be dropped, so a reparented grandchild `npm → node → frpc` is still in *this* box), and nothing outside the box is reachable. `(target others)` is the global form and is never emitted. The filter is **undocumented by Apple**, so the boundary is pinned by a functional test that starts a process *outside* any sandbox and asserts a box cannot signal it — same idiom as Chromium's `renderer.sb` and Apple's `application.sb`/`securityd.sb`. **(2) `ps`/`top` can't be exec'd at all**: they're setuid **root**, and Seatbelt denies exec of any setuid/setgid binary (`forbidden-exec-sugid`) *no matter how wide `process-exec` is* — Apple was asked for a de-privileging directive and said no. So clabox **removes** privilege instead of granting any: `proctools.ts` installs a setuid-less copy of `/bin/ps` into `<claboxHome>/bin` (first on the box's PATH). `ps` needs root only for **other users'** processes (`KERN_PROCARGS2`/`proc_pidinfo` are gated by `PRIV_GLOBAL_PROC_INFO`, same-uid lookups aren't), so the copy still shows everything the agent started and *less* than before — and it needs **no new profile rule**, since `<claboxHome>` already has the post-deny read + `process-exec` carve-out. **The copy must be re-signed or it dies:** `/bin/ps` carries the restricted entitlement `com.apple.system-task-ports.read`, honored only for Apple platform binaries, so AMFI SIGKILLs a plain copy (exit 137) — `codesign -f -s -` drops it; the install therefore stages into `<name>.new` and renames only after signing. `needsRefresh` compares **mtime only** (re-signing changes the size, so comparing that would reinstall on every launch). **(3) `pgrep`/`pkill` stay broken on purpose**: they'd only need `(allow mach-lookup (global-name "com.apple.sysmond"))`, but that's the one fix that opens a *new* channel out of the box, and the `ps` copy answers the same question without opening anything. See docs/troubleshooting.md
- **Entropy devices**: the `/dev access` block grants **read-only** `/dev/random` + `/dev/urandom` (the rest of `/dev` is limited to `tty*`/`null`/`zero`/`dtracehelper`). Language runtimes read these at startup — without the grant CPython fatals at preinit with `_Py_HashRandomization_Init: failed to get random numbers`, and Node `crypto`/openssl/git break too. Don't drop it
- **`ulimitProcs` is headroom, not an absolute cap** (`sandbox/run.ts#resolveUlimit`): macOS counts `RLIMIT_NPROC` per **uid, machine-wide**, and a desktop login already runs 1000+ processes — so `ulimit -u 1024` doesn't limit the box, it stops it forking at all from the first second. Claude's OAuth token is read by spawning `security`, so the box then reports `Not logged in · Please run /login` with an `API Usage Billing` header while the same account works fine outside. The launcher therefore sets `ulimit -u <countUserProcs() + ulimitProcs>`, clamped to `kern.maxprocperuid`, and sets **no** cap when the process count is unreadable. `clabox info` prints the effective value (`1024 (headroom) → ulimit -u 2101, 1077 procs running`). Don't turn it back into an absolute number
- **Background tasks are a sandbox ESCAPE, and are off by default** (`config.allowBackgroundTasks: false`, env `CLABOX_ALLOW_BACKGROUND_TASKS=1`): a Seatbelt profile is applied at `exec` and inherited, so it can never be dropped on a live process — but a background task isn't forked by the sandboxed claude at all. The request goes over the control socket to the singleton `claude daemon run` supervisor, which lives **outside every box** (PPID 1 / launchd), and it answers by launching `claude --fork-session --resume <same-session-id>`: same session id, same transcript, **no profile**. Measured ancestry of such a "sandboxed" session — `zsh ← claude --fork-session --resume ← ClaudeCode.app --bg-pty-host ← claude daemon run`, zero `sandbox-exec` in it — reading `~/Library/Logs/DiagnosticReports` and writing `~/Desktop` while still carrying the box's "you're in a sandbox" system prompt. Anything that detaches and re-attaches a session triggers it (tabbing away and back is enough). `run.ts#buildEnvArgs` therefore emits `utils/config.ts#SANDBOX_ESCAPE_GUARDS` (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`) unless the box opts in, and the profile no longer grants the daemon socket to a box that hasn't asked for `/rc` (see the networking note) — belt as well as braces, since the env guard lives inside the process the agent controls. **The opt-out has to be the config flag, not an `env` entry**: `env` takes its `-u` flags *ahead* of the assignments, so `env: { CLAUDE_CODE_DISABLE_BACKGROUND_TASKS: null }` emits `-u KEY … KEY=1` and leaves it set — only skipping the guard turns it off. Slogan: **Seatbelt binds to a process, a session binds to a transcript** — whenever the session outlives the process, the sandbox is left behind. See docs/troubleshooting.md
- **A config file is CODE RUN OUTSIDE THE SANDBOX, so it passes a trust gate** (`utils/trust.ts`, enforced by `loadConfig`): the file is `import()`ed *before* `sandbox-exec` is anywhere in the picture, its top-level code runs as the user, and what it returns **is** the sandbox policy. Three doors led there from a tree the agent can write — a repo's `./clabox.config.mjs` (auto-loaded by a bare `clabox`: `findConfigFile` probes the CWD), `-b ./boxes/vibe.mjs` (a documented feature), and `clabox init --dir <repo>`, which imports **every** config under `<repo>/configs` (`--no-apps` only skips the app build, not the import — so `git clone && clabox init` was RCE). Two independent checks now. **(1) Trust:** a config outside `claboxHomeDir()` must be recorded with `clabox trust <path>` into `<claboxHome>/trusted.json` (`0600`, stage+rename), keyed by **content hash** — an edit de-trusts it (`stale`) instead of riding the old approval; `--list` shows the records, `--remove` drops one. **(2) Box-writable:** after the merge, `assertConfigNotBoxWritable` refuses a config sitting inside a tree the *resulting* box can write (`boxWritableRoots` = project dir + `configDir` + `$TMPDIR` + every `write` grant, minus what the hard deny and the box's own `deny` bury). The config **file itself** is checked against the hard deny first (`hardDeniedPath`), and that is load-bearing: a whole-disk box (`paths: {'/': 'w'}`, the `root` preset) lists `/` as writable, so "is the config inside a writable tree?" is true for every config on the machine — including the ones under `~/.config/clabox`, which the same profile then takes back as read-only. Without the file-level check such a box refuses to start with "the agent could edit its own policy", which is exactly backwards: that is the one place it cannot write. That second check is the one for the symlinked-clabox-home layout: nominally the config is in the read-only home, physically it's in the repo, and Seatbelt matches the resolved path (`trust.ts#realpath` resolves as far as the path exists, so a missing last component can't hide a symlinked parent). `--trust` (env `CLABOX_TRUST=1`) bypasses both for one run — the escape hatch for a one-off and for CI. The profile *also* write-denies `clabox.config.*` inside the project (see `denyWriteGlobs`), so the plant shouldn't happen in the first place. `clabox info` prints the result as `configFile … (trust: home|trusted|accepted)`
- Config resolution, later wins: **defaults → env vars → JS config file** (`./clabox.config.mjs` or `~/.config/clabox/config.mjs`, or `CLABOX_CONFIG`, or the `--config` CLI flag which overrides `CLABOX_CONFIG`)
- **Ad-hoc env override `--env`/`-e` (repeatable, global)**: `-e KEY=VALUE` sets a var for this launch, a **bare `-e KEY` unsets it** (`env -u KEY`) — the only way to *drop* a var a shared preset or the login shell exported. Wired in `cli.ts#withCliPaths` → `utils/config.ts#withExtraEnv`, layered over `config.env` (CLI wins, later entries win, the split is on the **first** `=` so a value may contain more). `config.env` is therefore `Record<string, string | null>`, **`null` = unset**; `run.ts#buildEnvArgs` emits those as `-u KEY` **before** the assignments (`env` only accepts `-u` ahead of the `KEY=VALUE` list) and `daemon.ts#buildDaemonEnv` `delete`s them. The motivating case: claude turns feature-flag fetching off for `DISABLE_TELEMETRY` / `DO_NOT_TRACK` / `DISABLE_GROWTHBOOK` / `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, which hides Remote Control (`/rc`) and the other flag-gated features — and the first three count **any non-empty value**, `0`/`false` included, so only an unset re-enables them. One box, two tabs: `clabox -b ax-mg` (private) vs `clabox -b ax-mg -e DISABLE_TELEMETRY` (`/rc` works). **`--rc` is the shorthand**: it prepends an unset for every var in `utils/config.ts#FLAG_FETCH_BLOCKERS` (`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_TELEMETRY`, `DO_NOT_TRACK`, `DISABLE_GROWTHBOOK`) — **all four, because any single one from any source (box `env`, login shell, `settings.json`) is enough to block the fetch**, so clearing a subset looks like the fix didn't work — and it also sets `remoteControl: true`, which is what grants the daemon socket `/rc` talks over. They go *before* the `-e` entries, so an explicit `-e KEY=VALUE` still wins. See docs/troubleshooting.md
- **Tab decoration (`sandbox/tab.ts`, pure)** — a `--rc` tab is *remotely reachable* while a plain tab of the same box is private, and they otherwise look identical, so `--rc` is also forwarded to `runClaude` as the cosmetic `RunOptions.rc` and marks the tab: `buildTabDecor(config, {projectDir, rc})` → `{enter, leave, title, background, foreground, cursor}`, where `enter` = the title (`OSC 0`; `config.tab.title` or the `~`-shortened project dir, prefixed with `config.tab.rcBadge`) + the resolved colors — background `OSC 11`, foreground `OSC 10`, cursor `OSC 12` — and `leave` resets exactly the ones that were set (each reset is its code +100: `111`/`110`/`112`). Every color is a pair: `rc<X>` wins for `--rc` and falls back to the plain field when null. Defaults `rcBadge: '📡 RC'`, `rcBackground: '#5c1a00'`, `rcCursor: '#ff8c1a'` (bg + cursor on purpose: a box with `background-opacity`/blur washes the background out, a bright blinking cursor survives it; on macOS Ghostty the native tab takes the surface background, so `rcBackground` *is* the tab color), each overridable by `CLABOX_TAB_{TITLE,RC_BADGE,BACKGROUND,RC_BACKGROUND,FOREGROUND,RC_FOREGROUND,CURSOR,RC_CURSOR}` where an **empty** env value means "off". `normalizeColor` accepts only `#rgb`/`#rrggbb`/an X11 name and returns null otherwise — a color carrying `ESC`/`BEL` would be an injection point into the terminal stream, and cosmetics must never fail a launch. `run.ts` writes it **only when `process.stdout.isTTY`** and always writes `leave` after `spawnSync`. Claude rewrites the terminal title as it works (unless the box exports `CLAUDE_CODE_DISABLE_TERMINAL_TITLE`), so the **colors** are the durable marker and the badge is a hint
- **Echo guard around the handoff (`sandbox/tty.ts`)** — claude probes the terminal at startup (XTVERSION `CSI > 0 q`, an OSC 11 background query for light/dark, a DA1 `CSI c` flush sentinel) and reads the answers back off **stdin**. Those answers are input: anything arriving before claude has raw mode up — a window that's wider in a box, since every startup read goes through Seatbelt — is printed by the line discipline instead, so the welcome banner comes out as `^[P>|ghosttClaude1Code[v2.1.26352c ▐▛███▛█` (the terminal's own replies, `ESC` rendered as `^[` by ECHOCTL, interleaved with the logo). Ghostty answers in microseconds, so it shows there first. The launcher owns the terminal until the handoff, so `suppressEcho(sttyIo())` saves the termios (`stty -g`), applies `MUTE_ARGS`, and `restore()`s it in a `finally` around `spawnSync`. **`MUTE_ARGS` is `-echo -icanon`, and the `-icanon` is load-bearing**: ECHO off *with* canonical mode on is the exact termios signature of a password prompt, and Ghostty's `macos-auto-secure-input` (default on) `tcgetattr`s the pty and turns on macOS **Secure Input** (`EnableSecureEventInput`, the title-bar padlock that blocks every app from reading keyboard events) when it sees it — a plain `stty -echo` made every launch look like `sudo` asking for a password. Dropping ICANON too looks like the TUI it actually is; ISIG stays on, so Ctrl+C still works in the handoff window. Bonus effects: libuv snapshots the tty state on claude's **first** `setRawMode`, so claude's own raw-mode toggles restore *our* echo-less state; and a claude that dies without restoring the terminal no longer leaves the shell mute. Every `stty` failure (no tty, no saved state, `-echo` refused) degrades to `NO_GUARD` — a terminal stuck without echo would be worse than the garbled banner. `CLABOX_TTY_GUARD=0` opts out
- **In-sandbox notifications (`sandbox/notify.ts`, pure + `config.notify`)** — Notification Center is unreachable from a box (`terminal-notifier` hangs and wedges every later Stop hook; `osascript display notification` dies with `NSNotificationCenter connection invalid` — both want mach services a sandboxed process can't get), but the **terminal emulator runs outside the sandbox** and already reads a file the profile grants: the tty. Ghostty (verified 1.3.1) implements `OSC 777;notify` (a real banner), `OSC 9;4` (ConEmu progress on the tab/dock) and BEL (`bell-features`), so `buildNotifyHooks(config.notify, slug)` compiles them into claude hooks — `printf '\033]777;notify;…\a' > /dev/tty 2>/dev/null || true`. **`> /dev/tty` is the load-bearing part**: a hook's stdout is captured by claude, so a banner printed to stdout reaches nobody. `Stop` = banner + bell + progress cleared; `Notification` = banner + bell + progress parked at `paused` (a yellow tab survives being tabbed away from, a banner doesn't). `ttyWrite` escapes into a single-quoted `printf` format in a fixed order (backslash → `%` → ESC/BEL → `'`), `sanitizeOscText` strips control chars and the `;` field separator. `mergeHooks` concatenates per event, so a box's own `hooks` (e.g. `afplay`) keep firing. Opt-in (`notify.enabled`, env `CLABOX_NOTIFY=1`) because enabling it injects hooks into the box's compiled settings
- **Terminal-protocol hardening of app boxes (`init/ghostty.ts#GHOSTTY_SECURITY_DEFAULTS`)** — Seatbelt confines files and processes and has no idea the terminal protocol is **bidirectional**: an agent that can print to stdout can ask the emulator (which lives outside every box) to hand things back. `OSC 52` reads the **system clipboard**, `OSC 21` reports the window title. Both are gated by Ghostty config, so every generated app config emits `clipboard-read = deny` + `title-report = false` (plus `window-colorspace = display-p3` from `GHOSTTY_APP_DEFAULTS`), placed **after** the base `config-file` and **before** the box's own `app.ghostty` so a box can still override (scalar keys: last wins). Re-run `clabox init` after upgrading to get them into existing configs
- **`init` validates what it generated** (`init/app.ts#validateGhosttyConfig`): Ghostty does not fail on an unknown key, it logs and carries on — so a typo in `app.ghostty` silently half-applies. `init` runs the donor's own `<Ghostty.app>/Contents/MacOS/ghostty +validate-config --config-file=<generated>` and turns problems into a warning. Best-effort: no donor app, or a Ghostty without the subcommand, returns null
- **`tab` opens a box in the *running* Ghostty (`sandbox/applescript.ts`)** — the lightweight counterpart of an `app` box: no cloned bundle, just Ghostty's scripting dictionary (`Ghostty.sdef`, verified 1.3.1), which offers a `surface configuration` record (`command`, `initial working directory`, `initial input`, `environment variables`, `wait after command`) plus `new window` / `new tab` / `split` / `focus` / `input text` / `send key` / `perform action`. `buildOpenScript` is the pure text builder (`asQuote` drops control chars rather than escaping them — a newline would end the statement and let the rest run as its own command), `runAppleScript` is the only I/O and never throws. The surface runs the same `zsh -lic '…'` string as an app box (`init/ghostty.ts#buildShellCommand`, now shared), `--split` falls back to a new window when nothing is open, `--app` targets the box's own cloned bundle id, `--print` dumps the script instead of running it. `cli.ts#forwardedGlobals` re-emits the global flags (`--rc`, `-e`, `--ro`, `--rw`) into the launched command — they're parsed by the outer yargs and would otherwise never reach the box. Note `osascript` runs **outside** any box; a sandboxed agent can't reach it (the binary and the Apple-events mach service are both denied)
- **Ad-hoc path grants `--ro <path>` / `--rw <path>` / `--stat <path>` / `--socket <path>`** (all repeatable, global on `run`/`generate`/`profile`/`info`): append extra read / write / stat-only / socket-connect paths to the sandbox *without* a config file. Wired in `cli.ts#withCliPaths` → `utils/config.ts#withExtraPaths`, which is **additive** — it *concatenates* onto `config.paths.readOnly`/`readWrite`/`stat`/`socket` (unlike a config-file merge, where arrays *replace*), so an ad-hoc grant never wipes a box's own paths. `nargs: 1` per flag so a greedy array never swallows the subcommand or a trailing claude arg. The hard secret deny is still emitted last, so `--ro /` can't expose credentials and `--stat ~/.ssh` can't uncover `id_*`
- **The base policy is DATA, in its own module** (`policy/base.ts#BASE_PATH_GROUPS`, re-exported by `utils/config.ts`): every built-in path grant — `/`, `/System`, `/tmp`, `~/Library/Keychains`, `~/.gitconfig`, the `/dev` entries, the resolver socket — is a `path: rights` entry with a one-line note on *why* it's granted, grouped into the profile sections they're emitted as. `basePaths()` flattens them into `defaultConfig.paths`, so **a box can change the base policy**: narrow it (`'/System': 'r'`), widen it (`'/': 'w'`) or take it away (`'~/Library/Keychains': 'd'`). `profile.ts` is just the compiler — `grantBlock(table)` turns one table into SBPL, grouping paths that share rights into a single rule. Placement is what keeps overrides safe (SBPL = last-match-wins): a path left at its default is emitted in its own base section *before* the soft deny (`untouchedBaseKeys`), while an override travels with the box's own grants *after* it — so widening works, and a `'d'` lands in the soft deny tier where it buries the default. Rights letters beyond the config-facing four: `m` = `file-map-executable` (dyld needs it to map a library), `i` = `file-ioctl` (ttys), `l` = matcher is this path only rather than the tree, and a key starting with `^` is an SBPL regex. What stays in code, because it isn't static: the `xcode-select` toolchain, `config.configDir`, `config.bot.sshDir`, the project dir, clabox's own home, and the non-path grants (mach services, `sysctl-read`, `signal`, `process-info*`)
- **Per-path grants — `paths: { '<path>': '<rights>' }`** (`utils/config.ts#parsePathGrant`): the key is the path, the value its rights as a flag set — `r` read, `w` write, `s` stat-only, `e` exec, `d` deny — written `'rw'`, `['r','w']` or `['read','write']`. `resolvedPathRules` folds these into the same per-class lists the profile has always emitted, so both spellings mix freely in one object and nothing downstream changed. **Why prefer it:** a path sits on one line next to its rights, and a box building on a preset no longer spreads *per class* — `{...preset.paths, '~/x': 'w'}` instead of `{...preset.paths, readWrite: [...preset.paths.readWrite, '~/x'], exec: [...]}`. The **outer** spread is still required: spreading a preset inside a config file is plain JS, so `paths:` replaces the preset's object wholesale — clabox only deep-merges `defaultConfig` ⊕ the file (where path keys do survive, since `deepMerge` recurses into `paths` while arrays replace). Everything that could hide a typo throws instead: an unknown letter, an empty grant, `'d'` combined with a grant, and a key that is neither a known field nor path-shaped (`/`, `~`, `.`) — so `readWritte: [...]` is an error, not a silently-ignored "path"
- **Three access classes: `stat` ⊂ `read` ⊂ `write`** (`utils/config.ts#PathRules`, folded by `resolvedPathRules`, emitted in that order by `profile.ts`). SBPL's `file-read*` already includes `file-read-metadata`, so each wider class implies the ones below and a path only needs its widest class listed; a *deny* removes all three for the same reason. `read`/`write`/`stat` are the canonical config names, `readOnly`/`readWrite` remain aliases (concatenated, so existing boxes keep working), and `clabox info` prints the resolved `write`/`read`/`stat`/`exec`/`deny` lists. **`stat` used to be global and silently defeated every deny tier:** the introspection block carried a bare `(allow file-read-metadata)`, i.e. `stat(2)` over the whole disk, and since `file-read-metadata` and `file-read-data` are *separate operations*, denying `file-read*` hid contents but left existence/size/mode/mtime readable everywhere — a box that couldn't `ls ~/Library/Group Containers/<team>.com.1password` could still enumerate, file by file with sizes, what was in it. Now metadata comes only from a read/write grant, from `paths.stat` (`--stat`), or from the ancestors rule below. **Don't confuse it with the socket hole** (closed separately, see the networking note): a `connect()` to a unix socket is `network-outbound`, not a file op, so no file rule — stat, read or deny — ever governed it
- **`stat(2)` on granted paths' ancestors is the LAST file rule** (`profile.ts#pathAncestors`): a path lookup walks the chain, so resolving `~/.config/clabox/mcp/<box>.json` touches `~/.config` — which the hard deny covers — and the box's own `--mcp-config` would fail partway down. The final section therefore grants `file-read-metadata` on every directory *above* a granted path, emitted **after** the hard deny and the clabox-home carve-out. Always `literal`, never `subpath`: a stat-able ancestor must not drag its children in (that's the 1Password leak again), so `~/.ssh` is stat-able while `~/.ssh/id_ed25519` is not, and `~/Library` is while `~/Library/Group Containers/<anything>` is not. Paths that already carry a read grant are skipped. Inside `buildProfile`, allow rules build their matchers through the local `sp()`/`lit()` wrappers (bare `subpath`/`literal` + recording into the `granted` set) — a new allow rule that skips them still works, it just leaves its ancestors unstat-able, which shows up much later as an `EPERM` mid-path. Roots of `regex` rules carry no path to walk up from, so `/private/var/folders` (the `$TMPDIR` container) is registered by hand — without it `mkdtemp` fails
- `config.cwd` (env `CLABOX_CWD`, `~`-expanded → absolute; default null → shell CWD) sets the dir `claude` runs in and the dir granted RW as the project. `resolveProjectDir(config)` in `sandbox/run.ts` computes it (it delegates to `utils/config.ts#projectDirOf`, so the config layer can reason about the project dir without importing the launcher); `runClaude`/`generateProfile`/`profile` all key off it (and `spawnSync` runs with that `cwd`). Useful for named boxes that always target one project regardless of where `clabox` is invoked
- **Per-box MCP & pre-prompt & hooks** (one shared `configDir`, separate MCP/system-prompt/hooks per box): user config stays pure data — `config.mcp` (a `Record<string, McpServer>`), `config.systemPrompt` (`string | string[]`) and `config.hooks` (`HooksConfig` = claude's settings.json `hooks` map). `sandbox/extras.ts` is the pure builder: `buildBoxExtras(config, slug)` compiles `mcp` to `<claboxHome>/mcp/<slug>.json` and emits `--mcp-config <file>`, preceded by `--strict-mcp-config` unless the box sets **`strictMcp: false`** (env `CLABOX_STRICT_MCP=0`; default `true`), appends `systemPrompt` inline via `--append-system-prompt` (no file), and compiles `hooks` to `<claboxHome>/settings/<slug>.json` loaded with `--settings <file>`. **Hooks merge, not clobber:** a second `--settings` flag *replaces* the first (claude doesn't deep-merge them), so `readInlineSettings()` parses any inline `--settings` JSON already in `config.claudeArgs` (e.g. `{"includeCoAuthoredBy": false}`) and folds the hooks into it — emitted after `config.claudeArgs`, the file wins the last-`--settings`-takes-all race while preserving the inline settings. `slug` = `boxSlug(configFile, projectDir)` (config-file basename sans `.config.mjs`/`.mjs`, else project-dir basename). The json files live under clabox's **own** home — `<claboxHome>/{mcp,settings}/<slug>.json` where `claboxHome()` = `~/.config/clabox` (parent of `configsDir()`, honoring `CLABOX_CONFIGS_DIR`) — **not** the Claude `configDir`, so clabox never pollutes Claude's profile dir. Because `~/.config` is hard-denied in the sandbox, the profile re-grants **READ-ONLY** (+`process-exec`) to the whole `~/.config/clabox` home *after* the hard deny (`claboxHomeDir()`, see the deny-tiers note) so the box can read its own `--mcp-config`/`--settings`. **Never writable in-box** — clabox writes those json files from *outside* the sandbox before launch, so a write grant would buy nothing but let the agent rewrite its own box config (= its own sandbox policy). Materialized both at **run** (`run.ts#writeExtraFiles`, args spliced after `config.claudeArgs`, before CLI args) and at **init** (`scaffold.ts#materializeExtras`, slug = box name, best-effort per box). Arrays *replace* on merge, so presets can't pre-seed `mcp`; declare it on the box. Note `config.hooks` only **registers** the script with claude — for the script to actually run inside the sandbox its dir still needs an exec grant via `paths.exec` (and read via `paths.readOnly`); there is no dedicated `hooksDir` field.
- **`strictMcp: false` is what keeps the claude.ai cloud connectors** — `--strict-mcp-config` is documented as *"Only use MCP servers from `--mcp-config`, ignoring all other MCP configurations"*, and "all other configurations" is **wider than the config files**: it also drops the account's **claude.ai connectors** (Linear, Slack, Figma, Influencer Analytics — proxied via `mcp-proxy.anthropic.com`, `transport: claudeai-proxy` in the MCP logs, declared by no local file), leaving only the built-ins (`claude-in-chrome`, shown in `/mcp` under *"Built-in MCPs (always available)"*). So `config.mcp` is **not additive by default**: declaring a single server for a box silently costs it every cloud connector — verified on a box whose `~/Library/Caches/claude-cli-nodejs/<proj>/mcp-logs-claude-ai-*` stop getting sessions the moment `mcp` lands in its config. A box that wants its own server *alongside* the cloud ones sets `strictMcp: false` and gets a bare `--mcp-config`, which merges. Default stays `true` (the original point of the flag: with a shared `configDir`, each box loads exactly its own servers and no global/plugin ones)
- **Named boxes** (`-b`/`--box <name>`): resolve `<name>` to a config file in the global configs dir (`~/.config/clabox/configs/<name>.config.mjs`, falling back to `<name>.mjs`; dir overridable via `CLABOX_CONFIGS_DIR`) and feed it to `loadConfig` as the explicit config — so `-b` is a global shortcut that wins over `--config`. `_`-prefixed files are shared partials (e.g. `_presets.mjs`), not boxes, and a name outside `^[A-Za-z0-9][A-Za-z0-9._-]*$` is refused outright (it would end up inside a generated shell command — see the `init` validation note). **`-b` also takes a path** (so a repo can carry its own boxes, e.g. an alias `exec clabox -b path/vibe.mjs "$@"`): a ref ending in `.mjs` is an explicit config file used as-is (`~`-expanded, resolved against the CWD, must exist as a regular file — explicit intent, so even a `_*.mjs` is allowed, like `--config`); a ref containing `/` without the suffix is a dir-qualified name (`-b path/vibe` = box `vibe` inside `path/`, same `.config.mjs`-over-`.mjs` preference and `_`-partial refusal). Either path form is outside the clabox home, so it needs `clabox trust` (or `--trust`) first — see the trust note. `resolveBox`/`listBoxes`/`configsDir` live in `utils/config.ts`. (`init` defaults to the same global dir — `defaultBaseDir()` = the parent of `configsDir()` — so it works from any cwd; pass `--dir` for a project-local `<dir>/configs` layout.)
- **Glob read-deny (`paths.denyGlobs`)**: gitignore-style patterns that deny **read** of matching files/dirs *at any depth inside the project dir*. **Empty by default** (opt-in) — a box sets its own, e.g. `['**/.env*', '!**/.env.example', '**/___*']` (hide every `.env*` secret + triple-underscore `___*` files, keep the `.env.example` template). A `!`-prefix re-allows; last-match-wins mirrors `.gitignore`, so order matters. `sandbox/profile.ts#globToRegexBody` is the pure compiler (`*`=non-slash run, `**`=any run, `?`=one non-slash; a dir match also covers its contents); the section is emitted **after** the project RW grant (so it bites inside the project) but **before** the hard secret deny (so that stays supreme). **Scoped to the project on purpose** — a *global* match would also shadow system runtimes granted earlier (e.g. a double-underscore `**/__*` vs CPython's `.../__init__.py`) and break them; the triple-underscore `___*` convention deliberately dodges Python dunders. Patterns are pure data in the config; only the compiler lives in code
- **Glob write-deny (`paths.denyWriteGlobs`) — the one deny tier with a NON-empty default** (`utils/config.ts#DEFAULT_DENY_WRITE_GLOBS` = `['**/clabox.config.*', '**/.git/config', '**/.git/hooks', '**/.envrc']`): same compiler, same placement and the same `!`-re-allow as `denyGlobs`, but it takes `file-write*` only — the box keeps **reading** these files, it just can't change them. They share one property: **something outside the sandbox executes them later**, which turns a box-local write into unsandboxed code execution as the user. `clabox.config.*` is `import()`ed by the next launch before a profile exists; `.git/config` carries `core.pager` / `core.fsmonitor` / `core.sshCommand` / `core.hooksPath`, i.e. commands git runs — a `[core] pager = sh -c …` fires on the user's next `git log`, **in their own shell**; `.git/hooks` is the same thing by its canonical name (`git commit` runs them); `.envrc` is executed by direnv merely for `cd`-ing into the directory. None of it is something an agent needs to write to do its work. Trade-off to know: `git worktree add`, `git submodule add` and `git remote add` write `.git/config` and will fail in-box — a box that needs them sets its own `denyWriteGlobs`
- Two deny tiers (SBPL = last matching rule wins, so order is load-bearing): a **soft** privacy deny (`denyHome` dirs + `paths.deny`) is emitted *before* the extra `stat`/`read`/`write` grants and the project dir, so an explicit grant may override it (e.g. a project under `~/Documents`, or a broad `readOnly` for a debug box); a **hard** secret deny (`~/.ssh/id_*`, `*.pem`, `*.key`, `denyDotConfigs` credential dirs — which include `~/.config`) is emitted as the **last deny**, after every allow, so it always wins — personal credentials are never readable however wide the grants. Only the bot key subdir (not matched by the patterns) stays readable. The **only** rule after it is a carve-out re-granting **read-only** (+`process-exec`, so a box's hook scripts can live there and run) to the whole `~/.config/clabox` home — clabox's box configs **and** its compiled `mcp`/`settings` extras, otherwise blocked by the `~/.config` hard deny — so a box can read its own `--mcp-config`/`--settings` and exec its own hooks. **No write, on purpose:** the box configs *are* the sandbox policy, so an in-box write grant would let the sandboxed agent widen its own `paths`/`denyGlobs` for the next run; clabox materializes the compiled json from *outside* the sandbox (`run.ts#writeExtraFiles`, before `claude` starts), so nothing in-box ever needs to write here — edit box configs from an unsandboxed shell. Because a user `paths.readWrite` of `~/.config/clabox` is emitted *before* the hard deny, it can't punch through either (last-match-wins) — the post-deny carve-out is the only rule that survives, and it grants read only. It's scoped to the `clabox` subdir alone (the rest of `~/.config` — aws, gnupg, docker… — stays denied) and nothing credential-shaped lives there (secrets come from `env`, not files), so the invariant holds. **Symlinked home:** when `~/.config/clabox` is itself a symlink (e.g. relocated *into* a project repo so the box configs + compiled extras live in-tree), the files physically sit at the symlink target; Seatbelt matches the *resolved* path (the same reason `/tmp` **and** `/private/tmp` are both granted), so `resolvedClaboxHome()` adds the resolved target to that carve-out too — else the in-box read fails with `EPERM`. That layout also means the configs are physically inside a tree the box can write, which is what `assertConfigNotBoxWritable` refuses (see the trust note)
- **The profile is passed INLINE (`sandbox-exec -p`), never through a file in the launch path** (`run.ts#buildProfileText` / `#profilePath`): it used to be written to `$TMPDIR/clabox-<dir>-<hash>.sb`, and the base policy grants the whole `$TMPDIR` read-write — so the file holding a box's own policy was writable **by that box**, at a path derived deterministically from the project dir. Two ways that pays off: overwrite it with `(version 1)(allow default)` between the launcher's `writeFileSync` and `sandbox-exec -f` (several more fork/execs happen in between — extras, proctools, `ps`, `sysctl`, `stty` — and nothing reaps a process the box left running) and the next launch of that box runs claude **unsandboxed**; or plant a symlink there and have `writeFileSync` (no `O_EXCL`, no `O_NOFOLLOW`) truncate whatever it points at. The profile is ~8 KB against a 1 MB `ARG_MAX`, so the file bought nothing. `clabox generate` still materializes one for inspection — now at `<claboxHome>/profiles/clabox-<dir>-<hash>.sb` (read-only in-box, deterministic as before) and written `0600` through an `O_EXCL` stage + `rename`. `clabox info` reports it as `inline at launch — <path> (generate copy)`
- Tool-owned env vars use the `CLABOX_` prefix; `CLAUDE_CONFIG_DIR` is Claude's own var, passed straight through to `claude`. The app builder adds `CLABOX_GHOSTTY_APP`, `CLABOX_APPS_DIR`, `CLABOX_SIGN_ID`, `CLABOX_GHOSTTY_BASE_CONFIG`, `CLABOX_CLABOX_BIN` (defaults for `config.appBuilder`); the escape hatches and the trust gate add `CLABOX_ALLOW_OPEN`, `CLABOX_REMOTE_CONTROL` and `CLABOX_TRUST`
- The sandboxed `claude` inherits the shell env (sandbox-exec filters files/network, not env). `config.env` declares extra `KEY=VALUE` vars (e.g. `GITHUB_TOKEN`), appended last in `buildEnvArgs` so they win over the built-in hardening vars; a **`null` value means unset** (`env -u KEY`) — inheriting the shell env means a var can only be removed explicitly

## Dependencies

## Testing
- Framework: `bun:test` (`tests/` via `bunfig.toml`), run with `bun test` or `bun run test:unit`
- **Unit** tests check the generated SBPL text and run anywhere. **Functional** tests run a real `sandbox-exec` against a generated profile (`test.skipIf` auto-skips off macOS or when nested in a sandbox)
- The security-relevant invariants have functional tests of their own, and they are the ones that must not be left skipped: a box cannot start a process through `open` (SEC-1), cannot write `clabox.config.*` / `.git/config` / `.git/hooks` / `.envrc` inside its own project, and cannot signal a process outside the sandbox
