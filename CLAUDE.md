# clabox

> **This file contains instructions for AI assistants (Claude).** For project documentation see [docs/guideline.md](docs/guideline.md).

Run Claude Code in a sandbox for super-safe YOLO mode, configured in plain JavaScript.

**Important:**
- **ALWAYS** update this file and docs/guideline.md when changing scripts, structure, dependencies, commands, env vars, or the generated SBPL rules — do it in the same step, not after
- Runtime deps are **`yargs`** (CLI parsing) and **`@lsk4/log`** (pretty CLI logging, used only in `cli.ts`) — keep `@lsk4/log` out of `src/index.ts`/`src/info/` so the public `lib/index.js` stays dependency-light under the size-limit
- Run `bun run fix` and `bun run test` after each code change
- **Before saying "done"**, run the full `bun run test` (lint + types + unit + size). Functional tests shell out to real `sandbox-exec` and auto-skip off macOS or when nested in a sandbox — on macOS they must run, not be skipped
- Always write tests for new functionality — for profile changes, assert the generated SBPL text in `tests/profile.test.ts`
- Never invent SBPL rules: the profile must pass `sandbox-exec` validation. Test profile changes against real `sandbox-exec`
- Default to **Bun** for dev/test/build. The published `lib/` is plain ESM that runs on **Node ≥ 18**; the only runtime dependency is `yargs`

## Main Commands
```bash
bun install              # install deps (lockfile: bun.lock)
bun run build            # tsdown → lib/ (ESM + .d.ts + sourcemaps)
bun run test             # lint + types + unit + size (run before "done")
bun run fix              # biome check --write (format + lint + import order)
bun test                 # unit only (bun:test)
bun run cli -- profile   # run the CLI from source (also: generate, run, init)
bun run cli -- info      # print version + resolved box/config/extras diagnostics (via @lsk4/log)
bun run cli -- init      # gen clabox-<name> aliases + build Ghostty apps for `app` boxes
bun run cli -- init --no-apps        # aliases only (skip the Ghostty-app build)
bun run cli -- init --app "AX Manager" # (re)build just one app box
bun run cli -- -b ax-root # run a named box from ~/.config/clabox/configs/*.config.mjs
bun run cli -- -b ./boxes/vibe.mjs # run a box straight from a config-file path
bun run cli -- --ro ~/dir2 run       # ad-hoc read-only grant (repeatable)
bun run cli -- --ro ~/a --rw ~/b run # ad-hoc RO + RW grants (both repeatable)
bun run cli -- -b ax-mg --rc                    # unset ALL vars that block feature flags (→ /rc) + mark the tab
bun run cli -- -b ax-mg -e DISABLE_TELEMETRY    # unset a preset/shell var for THIS tab (→ /rc works)
bun run cli -- -b ax-mg -e DISABLE_TELEMETRY=1  # …or force it on for this tab only
bun run cli -- -b ax daemon          # claude's Remote Control daemon, OUTSIDE the sandbox
bun run cli -- --name ax daemon --detach # …in the background (`--name` is an alias of `-b`)
bun run cli -- -b ax daemon status   # passthrough: run | status | stop [--any] | logs
bun run cli -- -b ax-mg tab          # open that box in a new tab of the RUNNING Ghostty
bun run cli -- -b ax-mg tab --split right --rc  # …as an --rc split next to this one
bun run cli -- -b ax-mg tab --print  # print the AppleScript instead of running it
```

## Structure

**Rule:** Only entry-point files live in `src/` root — `index.ts` (public API aggregator) and `cli.ts` (the CLI, built to `lib/cli.js` = the `clabox` bin). All other code lives in subdirectories. The build emits to `lib/`; `bin`/`main`/`exports` point at built `lib/*.js`.

```
src/
├── index.ts              # public API aggregator — re-exports config/profile/run/init/info/daemon
├── cli.ts                # CLI entry (yargs): run / generate / profile / info / init / daemon / tab → lib/cli.js
├── sandbox/
│   ├── profile.ts        # pure SBPL profile builder + package-manager autodetect
│   ├── extras.ts         # pure: compile per-box `mcp`/`systemPrompt` → claude args + files
│   ├── tab.ts            # pure: tab title/background OSC builder — marks a `--rc` tab
│   ├── notify.ts         # pure: OSC 777 banner / OSC 9;4 progress / bell → hook commands
│   ├── applescript.ts    # pure builder + osascript I/O: open a box as a Ghostty tab/split
│   ├── tty.ts            # I/O: `stty -echo` guard over the launch handoff (+ restore)
│   └── run.ts            # I/O: locate claude/sandbox-exec, write profile + extras, launch it
├── info/
│   └── info.ts           # pure formatInfo + I/O gatherInfo/resolveClaboxPackage (`clabox info`)
├── daemon/
│   └── daemon.ts         # pure buildDaemonArgs/Env + I/O runDaemon — `claude daemon` UNsandboxed
├── init/
│   ├── aliases.ts        # pure builder for the `clabox init` shell aliases (text only)
│   ├── ghostty.ts        # pure builders: Ghostty config text + C launcher source + app paths

│   ├── app.ts            # I/O (macOS): clone Ghostty.app, swap binary, icon, codesign
│   └── scaffold.ts       # I/O: discover <base>/configs boxes, (re)write <base>/scripts/*, build apps
└── utils/

tests/
├── profile.test.ts       # bun:test — unit (profile text) + functional (real sandbox-exec)

```

## Key Architecture
- **7 CLI commands** (`run` / `generate` / `profile` / `info` / `init` / `daemon` / `tab`) over a pure builder (`sandbox/profile.ts`) and an I/O launcher (`sandbox/run.ts`) — keep that pure/I-O split
- **`info`** (`info/info.ts`) is the introspection report (who/what clabox is for the resolved config): `gatherInfo(config, {configFile, box})` does the I/O snapshot (resolve `claude`/`sandbox-exec` via `which`, `process.argv[1]`/`execPath`, profile path, compiled extras, tracked `CLABOX_*` env) and `formatInfo(data, {color})` is the pure aligned-text builder (color gated on a TTY). The CLI prints it through `@lsk4/log` (`createLogger('clabox').log(...)` for the table, `.warn(...)` when `claude`/`sandbox-exec` is missing). **Version + self-path** come from `resolveClaboxPackage()`, which **walks up from `import.meta.url` to the `package.json` whose `name === 'clabox'`** — a fixed `../../package.json` breaks once tsdown hoists the code into a hashed chunk (`lib/info-<hash>.js`) at a different depth; the walk survives the source tree, the built tree and an installed `node_modules/clabox/`
- `init` mirrors that split: `init/aliases.ts` + `init/ghostty.ts` are the pure text builders, `init/scaffold.ts` + `init/app.ts` do the fs/exec I/O. It discovers boxes in `<dir>/configs` (default `<dir>` = `defaultBaseDir()` = the parent of the global `configsDir()`, i.e. `~/.config/clabox`, honoring `CLABOX_CONFIGS_DIR`; overridable via `--dir` for a project-local `<dir>/configs` layout) via the same `listBoxes` rules as `-b` (both `<name>.mjs`/`<name>.config.mjs`, `_`-partials skipped) and (re)writes `<dir>/scripts/`: a source-able `index.sh` plus one `clabox-<name>.sh` wrapper per box. Each command runs `clabox -b <name>` — yolo vs. safe is decided by the box's own preset (`claudeArgs`), **not** by `init`. It prunes its own stale artifacts (`index.sh`, `clabox-*.sh`) on each run. **Paths are resolved at run time, not frozen at init time**: the `clabox` command is emitted bare so the shell's PATH resolves it at launch (survives package-manager moves, e.g. bun → npm/homebrew); `CLABOX_CONFIGS_DIR=<dir>` is baked **only when `<dir>/configs` doesn't already resolve (realpath, symlinks included) to the runtime default `~/.config/clabox/configs`** (`bakeConfigsDir`) — when it does, the prefix is omitted and `-b` finds the box via the default. The project `cd` dir stays absolute (it doesn't move with the package manager). An explicit `appBuilder.claboxBin` still pins an absolute binary path
- **Ghostty apps from `init`**: a box opts in by carrying an `app` object (`AppConfig`) in its config — only then does `init` `loadConfig` that box, write a Ghostty config to `<dir>/ghostty/<name>.config` (a `command = zsh -lic '…'` — login+interactive so the GUI app inherits the user's PATH, not launchd's minimal one — that `cd`s into `config.cwd` and runs `clabox -b <name>`; the `cwd`/`CLABOX_CONFIGS_DIR`/`claboxBin` are double-quoted (`ghostty.ts#shQuote`) so a spaced path like iCloud's `~/Library/Mobile Documents/…` doesn't split `cd` into two args (`string not in pwd`), plus `title`/`macos-icon`/extra lines from `app`), and build a cloned `<appsDir>/<name>.app` (replacing the old `ghostty-app-builder.sh`). The clone steps live in `init/app.ts` (macOS-only) and build into a staging `<name>.app.new` that is atomically `rename`d onto `<name>.app` **only after every step succeeds** — a failed build (e.g. an unreadable donor) never destroys the existing bundle: extract entitlements, `cp -R` Ghostty.app into the stage, patch `Info.plist`, swap the binary for a compiled C launcher (`init/ghostty.ts#buildLauncherSource`, bakes `--config-file=<config>`), set the icon (`.icns` copy or `.png`→`sips`+`iconutil`, then `plutil -remove CFBundleIconName` so macOS uses our loose `.icns` instead of the icon baked into Ghostty's `Assets.car`), disable Sparkle, `codesign` (`appBuilder.signId` or ad-hoc `-`). Machine-wide build settings live in `config.appBuilder`. It also writes a Raycast script command per app box to `<dir>/raycast/<name>.sh` (`init/raycast.ts#buildRaycastCommand`: `@raycast.*` metadata + `open <appPath>`; icon = `app.emoji` → the title's leading emoji → 👻). `--no-apps` skips the build; `--app <box|name>` (re)builds one. Builds are best-effort: if the host can't build (`canBuildApps`: not macOS / no Ghostty / no `cc`) or a build throws, it records a warning and still emits the aliases (and the ghostty config + raycast script, which point at where the app will live). It prunes its own `<dir>/ghostty/*.config` and `<dir>/raycast/*.sh` on a full run (not with `--app`, which would orphan other apps' artifacts). `.app` bundles are **not** auto-deleted
- **`daemon` runs claude's Remote Control supervisor OUTSIDE the sandbox** (`daemon/daemon.ts`, pure `buildDaemonArgs`/`buildDaemonEnv` + I/O `runDaemon`). Remote Control (`/rc`, sessions driven from the Claude app) needs a supervisor daemon; it's a **singleton per Claude config dir** (socket `/tmp/cc-daemon-<uid>/<hash(configDir)>/control.sock`) that claude starts **on demand**, so whoever asks first owns it. Born inside a box it is crippled two ways: (1) it probes its own start time by exec'ing `/bin/ps`, which is setgid `kmem` — Seatbelt refuses setgid execs however wide the `process-exec` grant is — so it logs `own process start-time probe failed twice — writing a procStart-less lock` and can no longer be stopped by `claude daemon stop`, while a new daemon "never displaces a running one"; (2) a macOS sandbox is **inherited and cannot be dropped**, so every worker it spawns for a remote session stays confined to *that* box's profile and dies on another project (`bg settled … (crashed): exit 1 before init`). `clabox -b <box> daemon [run|status|stop [--any]|logs]` therefore spawns `claude daemon …` with the box's `configDir` + `config.env` but **no `sandbox-exec` and no `ulimit`**; `--detach` backgrounds it (`spawn` + `detached` + `stdio: 'ignore'` + `unref`, output goes to `<configDir>/daemon.log`). Start it before/independently of the boxes and their `/rc` reuses it. `--name` is an alias of `-b`/`--box`
- The Seatbelt profile starts with `(deny default)` — nothing is allowed unless an explicit rule grants it
- **Claude runtime state (RW)**: `~/.local/state/claude` (claude's startup version lock — it writes a `.lock.tmp.<rand>`, so RO isn't enough) and `~/Library/Caches/claude-cli-nodejs` (per-MCP-server log batches). Both are claude-owned scratch dirs with no credentials in them (OAuth tokens live in the keychain); `~/.cache/claude` stays RO. Symptoms of dropping these: `NON-FATAL: Lock acquisition failed` / `Dropping log batch for …` in `<configDir>/debug/latest`
- **Active toolchain grant (`profile.ts#resolvedDeveloperDirs`)**: `/Library/Developer/CommandLineTools` + `/Applications/Xcode.app` are granted statically, but `/usr/bin/python3` (like `clang`/`git`/`swift`) is a **shim that execs whatever `xcode-select -p` selects** — and Seatbelt matches the **symlink-resolved** path. On a dev mac `Xcode.app` is a real directory, so the static grant covers it; on a CI runner the bundle is versioned (`/Applications/Xcode_16.4.app`) with `Xcode.app` a symlink onto it, the static grant resolves to nothing, and CPython dies at preinit — which showed up as the entropy regression test passing locally and failing only in CI. So the profile also grants the realpath of `/var/db/xcode_select_link` (the link `xcode-select` maintains — read via `fs`, not by shelling out), minus whatever is already static. Same class of bug as the resolved clabox home
- **Entropy devices**: the `/dev access` block grants **read-only** `/dev/random` + `/dev/urandom` (the rest of `/dev` is limited to `tty*`/`null`/`zero`/`dtracehelper`). Language runtimes read these at startup — without the grant CPython fatals at preinit with `_Py_HashRandomization_Init: failed to get random numbers`, and Node `crypto`/openssl/git break too. Don't drop it
- **`ulimitProcs` is headroom, not an absolute cap** (`sandbox/run.ts#resolveUlimit`): macOS counts `RLIMIT_NPROC` per **uid, machine-wide**, and a desktop login already runs 1000+ processes — so `ulimit -u 1024` doesn't limit the box, it stops it forking at all from the first second. Claude's OAuth token is read by spawning `security`, so the box then reports `Not logged in · Please run /login` with an `API Usage Billing` header while the same account works fine outside. The launcher therefore sets `ulimit -u <countUserProcs() + ulimitProcs>`, clamped to `kern.maxprocperuid`, and sets **no** cap when the process count is unreadable. `clabox info` prints the effective value (`1024 (headroom) → ulimit -u 2101, 1077 procs running`). Don't turn it back into an absolute number
- **Background tasks are a sandbox ESCAPE, and are off by default** (`config.allowBackgroundTasks: false`, env `CLABOX_ALLOW_BACKGROUND_TASKS=1`): a Seatbelt profile is applied at `exec` and inherited, so it can never be dropped on a live process — but a background task isn't forked by the sandboxed claude at all. The request goes over the control socket to the singleton `claude daemon run` supervisor, which lives **outside every box** (PPID 1 / launchd), and it answers by launching `claude --fork-session --resume <same-session-id>`: same session id, same transcript, **no profile**. Measured ancestry of such a "sandboxed" session — `zsh ← claude --fork-session --resume ← ClaudeCode.app --bg-pty-host ← claude daemon run`, zero `sandbox-exec` in it — reading `~/Library/Logs/DiagnosticReports` and writing `~/Desktop` while still carrying the box's "you're in a sandbox" system prompt. Anything that detaches and re-attaches a session triggers it (tabbing away and back is enough). `run.ts#buildEnvArgs` therefore emits `utils/config.ts#SANDBOX_ESCAPE_GUARDS` (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`) unless the box opts in. **The opt-out has to be the config flag, not an `env` entry**: `env` takes its `-u` flags *ahead* of the assignments, so `env: { CLAUDE_CODE_DISABLE_BACKGROUND_TASKS: null }` emits `-u KEY … KEY=1` and leaves it set — only skipping the guard turns it off. Slogan: **Seatbelt binds to a process, a session binds to a transcript** — whenever the session outlives the process, the sandbox is left behind. See docs/troubleshooting.md
- Config resolution, later wins: **defaults → env vars → JS config file** (`./clabox.config.mjs` or `~/.config/clabox/config.mjs`, or `CLABOX_CONFIG`, or the `--config` CLI flag which overrides `CLABOX_CONFIG`)
- **Ad-hoc env override `--env`/`-e` (repeatable, global)**: `-e KEY=VALUE` sets a var for this launch, a **bare `-e KEY` unsets it** (`env -u KEY`) — the only way to *drop* a var a shared preset or the login shell exported. Wired in `cli.ts#withCliPaths` → `utils/config.ts#withExtraEnv`, layered over `config.env` (CLI wins, later entries win, the split is on the **first** `=` so a value may contain more). `config.env` is therefore `Record<string, string | null>`, **`null` = unset**; `run.ts#buildEnvArgs` emits those as `-u KEY` **before** the assignments (`env` only accepts `-u` ahead of the `KEY=VALUE` list) and `daemon.ts#buildDaemonEnv` `delete`s them. The motivating case: claude turns feature-flag fetching off for `DISABLE_TELEMETRY` / `DO_NOT_TRACK` / `DISABLE_GROWTHBOOK` / `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, which hides Remote Control (`/rc`) and the other flag-gated features — and the first three count **any non-empty value**, `0`/`false` included, so only an unset re-enables them. One box, two tabs: `clabox -b ax-mg` (private) vs `clabox -b ax-mg -e DISABLE_TELEMETRY` (`/rc` works). **`--rc` is the shorthand**: it prepends an unset for every var in `utils/config.ts#FLAG_FETCH_BLOCKERS` (`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_TELEMETRY`, `DO_NOT_TRACK`, `DISABLE_GROWTHBOOK`) — **all four, because any single one from any source (box `env`, login shell, `settings.json`) is enough to block the fetch**, so clearing a subset looks like the fix didn't work. They go *before* the `-e` entries, so an explicit `-e KEY=VALUE` still wins. See docs/troubleshooting.md
- **Tab decoration (`sandbox/tab.ts`, pure)** — a `--rc` tab is *remotely reachable* while a plain tab of the same box is private, and they otherwise look identical, so `--rc` is also forwarded to `runClaude` as the cosmetic `RunOptions.rc` and marks the tab: `buildTabDecor(config, {projectDir, rc})` → `{enter, leave, title, background, foreground, cursor}`, where `enter` = the title (`OSC 0`; `config.tab.title` or the `~`-shortened project dir, prefixed with `config.tab.rcBadge`) + the resolved colors — background `OSC 11`, foreground `OSC 10`, cursor `OSC 12` — and `leave` resets exactly the ones that were set (each reset is its code +100: `111`/`110`/`112`). Every color is a pair: `rc<X>` wins for `--rc` and falls back to the plain field when null. Defaults `rcBadge: '📡 RC'`, `rcBackground: '#5c1a00'`, `rcCursor: '#ff8c1a'` (bg + cursor on purpose: a box with `background-opacity`/blur washes the background out, a bright blinking cursor survives it; on macOS Ghostty the native tab takes the surface background, so `rcBackground` *is* the tab color), each overridable by `CLABOX_TAB_{TITLE,RC_BADGE,BACKGROUND,RC_BACKGROUND,FOREGROUND,RC_FOREGROUND,CURSOR,RC_CURSOR}` where an **empty** env value means "off". `normalizeColor` accepts only `#rgb`/`#rrggbb`/an X11 name and returns null otherwise — a color carrying `ESC`/`BEL` would be an injection point into the terminal stream, and cosmetics must never fail a launch. `run.ts` writes it **only when `process.stdout.isTTY`** and always writes `leave` after `spawnSync`. Claude rewrites the terminal title as it works (unless the box exports `CLAUDE_CODE_DISABLE_TERMINAL_TITLE`), so the **colors** are the durable marker and the badge is a hint
- **Echo guard around the handoff (`sandbox/tty.ts`)** — claude probes the terminal at startup (XTVERSION `CSI > 0 q`, an OSC 11 background query for light/dark, a DA1 `CSI c` flush sentinel) and reads the answers back off **stdin**. Those answers are input: anything arriving before claude has raw mode up — a window that's wider in a box, since every startup read goes through Seatbelt — is printed by the line discipline instead, so the welcome banner comes out as `^[P>|ghosttClaude1Code[v2.1.26352c ▐▛███▛█` (the terminal's own replies, `ESC` rendered as `^[` by ECHOCTL, interleaved with the logo). Ghostty answers in microseconds, so it shows there first. The launcher owns the terminal until the handoff, so `suppressEcho(sttyIo())` saves the termios (`stty -g`), applies `MUTE_ARGS`, and `restore()`s it in a `finally` around `spawnSync`. **`MUTE_ARGS` is `-echo -icanon`, and the `-icanon` is load-bearing**: ECHO off *with* canonical mode on is the exact termios signature of a password prompt, and Ghostty's `macos-auto-secure-input` (default on) `tcgetattr`s the pty and turns on macOS **Secure Input** (`EnableSecureEventInput`, the title-bar padlock that blocks every app from reading keyboard events) when it sees it — a plain `stty -echo` made every launch look like `sudo` asking for a password. Dropping ICANON too looks like the TUI it actually is; ISIG stays on, so Ctrl+C still works in the handoff window. Bonus effects: libuv snapshots the tty state on claude's **first** `setRawMode`, so claude's own raw-mode toggles restore *our* echo-less state; and a claude that dies without restoring the terminal no longer leaves the shell mute. Every `stty` failure (no tty, no saved state, `-echo` refused) degrades to `NO_GUARD` — a terminal stuck without echo would be worse than the garbled banner. `CLABOX_TTY_GUARD=0` opts out
- **In-sandbox notifications (`sandbox/notify.ts`, pure + `config.notify`)** — Notification Center is unreachable from a box (`terminal-notifier` hangs and wedges every later Stop hook; `osascript display notification` dies with `NSNotificationCenter connection invalid` — both want mach services a sandboxed process can't get), but the **terminal emulator runs outside the sandbox** and already reads a file the profile grants: the tty. Ghostty (verified 1.3.1) implements `OSC 777;notify` (a real banner), `OSC 9;4` (ConEmu progress on the tab/dock) and BEL (`bell-features`), so `buildNotifyHooks(config.notify, slug)` compiles them into claude hooks — `printf '\033]777;notify;…\a' > /dev/tty 2>/dev/null || true`. **`> /dev/tty` is the load-bearing part**: a hook's stdout is captured by claude, so a banner printed to stdout reaches nobody. `Stop` = banner + bell + progress cleared; `Notification` = banner + bell + progress parked at `paused` (a yellow tab survives being tabbed away from, a banner doesn't). `ttyWrite` escapes into a single-quoted `printf` format in a fixed order (backslash → `%` → ESC/BEL → `'`), `sanitizeOscText` strips control chars and the `;` field separator. `mergeHooks` concatenates per event, so a box's own `hooks` (e.g. `afplay`) keep firing. Opt-in (`notify.enabled`, env `CLABOX_NOTIFY=1`) because enabling it injects hooks into the box's compiled settings
- **Terminal-protocol hardening of app boxes (`init/ghostty.ts#GHOSTTY_SECURITY_DEFAULTS`)** — Seatbelt confines files and processes and has no idea the terminal protocol is **bidirectional**: an agent that can print to stdout can ask the emulator (which lives outside every box) to hand things back. `OSC 52` reads the **system clipboard**, `OSC 21` reports the window title. Both are gated by Ghostty config, so every generated app config emits `clipboard-read = deny` + `title-report = false` (plus `window-colorspace = display-p3` from `GHOSTTY_APP_DEFAULTS`), placed **after** the base `config-file` and **before** the box's own `app.ghostty` so a box can still override (scalar keys: last wins). Re-run `clabox init` after upgrading to get them into existing configs
- **`init` validates what it generated** (`init/app.ts#validateGhosttyConfig`): Ghostty does not fail on an unknown key, it logs and carries on — so a typo in `app.ghostty` silently half-applies. `init` runs the donor's own `<Ghostty.app>/Contents/MacOS/ghostty +validate-config --config-file=<generated>` and turns problems into a warning. Best-effort: no donor app, or a Ghostty without the subcommand, returns null
- **`tab` opens a box in the *running* Ghostty (`sandbox/applescript.ts`)** — the lightweight counterpart of an `app` box: no cloned bundle, just Ghostty's scripting dictionary (`Ghostty.sdef`, verified 1.3.1), which offers a `surface configuration` record (`command`, `initial working directory`, `initial input`, `environment variables`, `wait after command`) plus `new window` / `new tab` / `split` / `focus` / `input text` / `send key` / `perform action`. `buildOpenScript` is the pure text builder (`asQuote` drops control chars rather than escaping them — a newline would end the statement and let the rest run as its own command), `runAppleScript` is the only I/O and never throws. The surface runs the same `zsh -lic '…'` string as an app box (`init/ghostty.ts#buildShellCommand`, now shared), `--split` falls back to a new window when nothing is open, `--app` targets the box's own cloned bundle id, `--print` dumps the script instead of running it. `cli.ts#forwardedGlobals` re-emits the global flags (`--rc`, `-e`, `--ro`, `--rw`) into the launched command — they're parsed by the outer yargs and would otherwise never reach the box. Note `osascript` runs **outside** any box; a sandboxed agent can't reach it (the binary and the Apple-events mach service are both denied)
- **Ad-hoc path grants `--ro <path>` / `--rw <path>`** (both repeatable, global on `run`/`generate`/`profile`/`info`): append extra read-only / read-write paths to the sandbox *without* a config file. Wired in `cli.ts#withCliPaths` → `utils/config.ts#withExtraPaths`, which is **additive** — it *concatenates* onto `config.paths.readOnly`/`readWrite` (unlike a config-file merge, where arrays *replace*), so an ad-hoc grant never wipes a box's own paths. `nargs: 1` per flag so a greedy array never swallows the subcommand or a trailing claude arg. The hard secret deny is still emitted last, so `--ro /` can't expose credentials
- `config.cwd` (env `CLABOX_CWD`, `~`-expanded → absolute; default null → shell CWD) sets the dir `claude` runs in and the dir granted RW as the project. `resolveProjectDir(config)` in `sandbox/run.ts` computes it; `runClaude`/`generateProfile`/`profile` all key off it (and `spawnSync` runs with that `cwd`). Useful for named boxes that always target one project regardless of where `clabox` is invoked
- **Per-box MCP & pre-prompt & hooks** (one shared `configDir`, separate MCP/system-prompt/hooks per box): user config stays pure data — `config.mcp` (a `Record<string, McpServer>`), `config.systemPrompt` (`string | string[]`) and `config.hooks` (`HooksConfig` = claude's settings.json `hooks` map). `sandbox/extras.ts` is the pure builder: `buildBoxExtras(config, slug)` compiles `mcp` to `<claboxHome>/mcp/<slug>.json` and emits `--mcp-config <file>`, preceded by `--strict-mcp-config` unless the box sets **`strictMcp: false`** (env `CLABOX_STRICT_MCP=0`; default `true`), appends `systemPrompt` inline via `--append-system-prompt` (no file), and compiles `hooks` to `<claboxHome>/settings/<slug>.json` loaded with `--settings <file>`. **Hooks merge, not clobber:** a second `--settings` flag *replaces* the first (claude doesn't deep-merge them), so `readInlineSettings()` parses any inline `--settings` JSON already in `config.claudeArgs` (e.g. `{"includeCoAuthoredBy": false}`) and folds the hooks into it — emitted after `config.claudeArgs`, the file wins the last-`--settings`-takes-all race while preserving the inline settings. `slug` = `boxSlug(configFile, projectDir)` (config-file basename sans `.config.mjs`/`.mjs`, else project-dir basename). The json files live under clabox's **own** home — `<claboxHome>/{mcp,settings}/<slug>.json` where `claboxHome()` = `~/.config/clabox` (parent of `configsDir()`, honoring `CLABOX_CONFIGS_DIR`) — **not** the Claude `configDir`, so clabox never pollutes Claude's profile dir. Because `~/.config` is hard-denied in the sandbox, the profile re-grants **READ-ONLY** (+`process-exec`) to the whole `~/.config/clabox` home *after* the hard deny (`claboxHomeDir()`, see the deny-tiers note) so the box can read its own `--mcp-config`/`--settings`. **Never writable in-box** — clabox writes those json files from *outside* the sandbox before launch, so a write grant would buy nothing but let the agent rewrite its own box config (= its own sandbox policy). Materialized both at **run** (`run.ts#writeExtraFiles`, args spliced after `config.claudeArgs`, before CLI args) and at **init** (`scaffold.ts#materializeExtras`, slug = box name, best-effort per box). Arrays *replace* on merge, so presets can't pre-seed `mcp`; declare it on the box. Note `config.hooks` only **registers** the script with claude — for the script to actually run inside the sandbox its dir still needs an exec grant via `paths.exec` (and read via `paths.readOnly`); there is no dedicated `hooksDir` field.
- **`strictMcp: false` is what keeps the claude.ai cloud connectors** — `--strict-mcp-config` is documented as *"Only use MCP servers from `--mcp-config`, ignoring all other MCP configurations"*, and "all other configurations" is **wider than the config files**: it also drops the account's **claude.ai connectors** (Linear, Slack, Figma, Influencer Analytics — proxied via `mcp-proxy.anthropic.com`, `transport: claudeai-proxy` in the MCP logs, declared by no local file), leaving only the built-ins (`claude-in-chrome`, shown in `/mcp` under *"Built-in MCPs (always available)"*). So `config.mcp` is **not additive by default**: declaring a single server for a box silently costs it every cloud connector — verified on a box whose `~/Library/Caches/claude-cli-nodejs/<proj>/mcp-logs-claude-ai-*` stop getting sessions the moment `mcp` lands in its config. A box that wants its own server *alongside* the cloud ones sets `strictMcp: false` and gets a bare `--mcp-config`, which merges. Default stays `true` (the original point of the flag: with a shared `configDir`, each box loads exactly its own servers and no global/plugin ones)
- **Named boxes** (`-b`/`--box <name>`): resolve `<name>` to a config file in the global configs dir (`~/.config/clabox/configs/<name>.config.mjs`, falling back to `<name>.mjs`; dir overridable via `CLABOX_CONFIGS_DIR`) and feed it to `loadConfig` as the explicit config — so `-b` is a global shortcut that wins over `--config`. `_`-prefixed files are shared partials (e.g. `_presets.mjs`), not boxes. **`-b` also takes a path** (so a repo can carry its own boxes, e.g. an alias `exec clabox -b path/vibe.mjs "$@"`): a ref ending in `.mjs` is an explicit config file used as-is (`~`-expanded, resolved against the CWD, must exist as a regular file — explicit intent, so even a `_*.mjs` is allowed, like `--config`); a ref containing `/` without the suffix is a dir-qualified name (`-b path/vibe` = box `vibe` inside `path/`, same `.config.mjs`-over-`.mjs` preference and `_`-partial refusal). `resolveBox`/`listBoxes`/`configsDir` live in `utils/config.ts`. (`init` defaults to the same global dir — `defaultBaseDir()` = the parent of `configsDir()` — so it works from any cwd; pass `--dir` for a project-local `<dir>/configs` layout.)
- **Glob read-deny (`paths.denyGlobs`)**: gitignore-style patterns that deny **read** of matching files/dirs *at any depth inside the project dir*. **Empty by default** (opt-in) — a box sets its own, e.g. `['**/.env*', '!**/.env.example', '**/___*']` (hide every `.env*` secret + triple-underscore `___*` files, keep the `.env.example` template). A `!`-prefix re-allows; last-match-wins mirrors `.gitignore`, so order matters. `sandbox/profile.ts#globToRegexBody` is the pure compiler (`*`=non-slash run, `**`=any run, `?`=one non-slash; a dir match also covers its contents); the section is emitted **after** the project RW grant (so it bites inside the project) but **before** the hard secret deny (so that stays supreme). **Scoped to the project on purpose** — a *global* match would also shadow system runtimes granted earlier (e.g. a double-underscore `**/__*` vs CPython's `.../__init__.py`) and break them; the triple-underscore `___*` convention deliberately dodges Python dunders. Patterns are pure data in the config; only the compiler lives in code
- Two deny tiers (SBPL = last matching rule wins, so order is load-bearing): a **soft** privacy deny (`denyHome` dirs + `paths.deny`) is emitted *before* the extra `readOnly`/`readWrite` and the project dir, so an explicit grant may override it (e.g. a project under `~/Documents`, or a broad `readOnly` for a debug box); a **hard** secret deny (`~/.ssh/id_*`, `*.pem`, `*.key`, `denyDotConfigs` credential dirs — which include `~/.config`) is emitted as the **last deny**, after every allow, so it always wins — personal credentials are never readable however wide the grants. Only the bot key subdir (not matched by the patterns) stays readable. The **only** rule after it is a carve-out re-granting **read-only** (+`process-exec`, so a box's hook scripts can live there and run) to the whole `~/.config/clabox` home — clabox's box configs **and** its compiled `mcp`/`settings` extras, otherwise blocked by the `~/.config` hard deny — so a box can read its own `--mcp-config`/`--settings` and exec its own hooks. **No write, on purpose:** the box configs *are* the sandbox policy, so an in-box write grant would let the sandboxed agent widen its own `paths`/`denyGlobs` for the next run; clabox materializes the compiled json from *outside* the sandbox (`run.ts#writeExtraFiles`, before `claude` starts), so nothing in-box ever needs to write here — edit box configs from an unsandboxed shell. Because a user `paths.readWrite` of `~/.config/clabox` is emitted *before* the hard deny, it can't punch through either (last-match-wins) — the post-deny carve-out is the only rule that survives, and it grants read only. It's scoped to the `clabox` subdir alone (the rest of `~/.config` — aws, gnupg, docker… — stays denied) and nothing credential-shaped lives there (secrets come from `env`, not files), so the invariant holds. **Symlinked home:** when `~/.config/clabox` is itself a symlink (e.g. relocated *into* a project repo so the box configs + compiled extras live in-tree), the files physically sit at the symlink target; Seatbelt matches the *resolved* path (the same reason `/tmp` **and** `/private/tmp` are both granted), so `resolvedClaboxHome()` adds the resolved target to that carve-out too — else the in-box read fails with `EPERM`
- Profiles are deterministic per project: `$TMPDIR/clabox-<dir>-<hash>.sb` (sha256 of the absolute project path)
- Tool-owned env vars use the `CLABOX_` prefix; `CLAUDE_CONFIG_DIR` is Claude's own var, passed straight through to `claude`. The app builder adds `CLABOX_GHOSTTY_APP`, `CLABOX_APPS_DIR`, `CLABOX_SIGN_ID`, `CLABOX_GHOSTTY_BASE_CONFIG`, `CLABOX_CLABOX_BIN` (defaults for `config.appBuilder`)
- The sandboxed `claude` inherits the shell env (sandbox-exec filters files/network, not env). `config.env` declares extra `KEY=VALUE` vars (e.g. `GITHUB_TOKEN`), appended last in `buildEnvArgs` so they win over the built-in hardening vars; a **`null` value means unset** (`env -u KEY`) — inheriting the shell env means a var can only be removed explicitly

## Dependencies
- `yargs` — CLI command/flag parsing
- `@lsk4/log` — pretty leveled CLI logging; imported **only in `cli.ts`** (the `info` command's output sink), so it never reaches the public `lib/index.js` bundle

## Testing
- Framework: `bun:test` (`tests/` via `bunfig.toml`), run with `bun test` or `bun run test:unit`
- **Unit** tests check the generated SBPL text and run anywhere. **Functional** tests run a real `sandbox-exec` against a generated profile (`test.skipIf` auto-skips off macOS or when nested in a sandbox)
